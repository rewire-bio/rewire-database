# Information architecture and content hierarchy review

Scope: read-only source review at fd7f12c in rewire-contributions. AGENTS.md read. No product changes, browser operation, or claims of visual/assistive-technology testing. References are relative to this repository.

## Main diagnosis

The wall of text is principally a hierarchy problem. The site exposes its record schema and its evidence maintenance process at the same level as the reader's decision. Progressive disclosure already improves model pages, but benchmark/task/protocol pages still default to expansive tables, narrative sections, recipes, gap reports and source histories. Adding more charts alone will not address this.

## Prioritized findings

1. **P1 — Benchmark pages use the dense version of the template.** Profile facts, all mechanism explanations, the evidence table and source history are open by default for non-predictive records. Charts and up to 25 result rows precede the benchmark overview. A reader must consume the measurements before learning what the test measures. Evidence: components/catalogue/Profile.tsx:229 and :313; app/database/[kind]/[id]/page.tsx:403, :420, :454, :729 and :743; components/catalogue/EvidenceTable.tsx:73. Fix: consistent compact overview for every core entity, followed by Results, How to run, Evidence. Keep exact protocol, cohort and critical caveats visible beside any chart; collapse narrative details, full provenance and historical material.

2. **P1 — Search asks visitors to understand 16 record kinds before finding anything.** Four main kind buttons and twelve secondary kind buttons appear before search; cards expose status, unbounded summary and source counts but no immediate evaluation availability. Evidence: lib/omics-browse.ts:116–135; app/database/Explorer.tsx:142–218, :293–343. Fix: search near the top, four primary views, an explicit 'More record types' disclosure, and compact rows with research area, short purpose and 'N evaluations / no linked evaluations'. Keep methods, configurations, services and pipelines semantically distinct; make their advanced taxonomy optional rather than merging the records.

3. **P1 — Filtered-zero results falsely describe the evidence collection.** Results.tsx:173–175 always says 'No evaluations linked in this release' when data.total is zero, including a filter combination that yields no rows. There is no reset action. Fix: distinguish initial.total===0 from a filtered-empty state; say 'No results match these filters', preserve the unfiltered count and offer Reset filters. For genuinely empty records show reviewed source links and next useful action; absence of linked data is not poor performance.

4. **P1 — Result tables are long-form documents inside cells.** Every evaluation group prints entity links, its protocol paragraph, origin and review metadata. Each metric row then includes unit, direction, aggregation, uncertainty, scored/eligible figures, source citation and concern text. This creates high vertical cost even with only 25 rows. Evidence: components/catalogue/Results.tsx:192–300; app/database/database.module.css:338–345. Fix: choose an evaluation/protocol first; present compact numeric rows under a compact protocol summary; show per-row evidence/uncertainty detail on demand. Never hide missing coverage or a material source concern merely to shorten the table.

5. **P2 — Navigation loses context and has conditional dead ends.** Detail breadcrumbs reconstruct only kind and omit the user's search/area/status; Explorer uses replaceState and keeps cursor solely in memory. Detail links to How it works and Strengths and limitations are unconditional for entities, while Profile returns null for those parts when profile parsing fails. The top nav's Database active state only matches '/', not '/database/...', and does not set aria-current. Evidence: app/database/Explorer.tsx:128–139, :346–370; app/database/[kind]/[id]/page.tsx:251–255, :315–337; components/catalogue/Profile.tsx:65–79; components/header.tsx:20–24. Fix: retain browse URL/page state, add Back to results, derive section navigation from actually rendered sections, and mark current navigation semantically. Dead-anchor behavior is code-confirmed conditional, not verified against a particular current record.

6. **P2 — Page navigation is an equal-weight link wrap that disappears during long reading.** Detail section nav can expose roughly ten links with no group hierarchy or active-section state, and is not sticky; result/evaluation records lack this nav entirely because they are not profileKinds. Evidence: app/database/[kind]/[id]/page.tsx:115, :314–338; app/database/database.module.css:292–299. Fix: four task-level destinations, sticky desktop local navigation and a compact mobile section menu. Use actual section availability. Group Papers, claims, sources, review history and technical receipts under Evidence.

7. **P2 — Sparse chart states are unexplained.** BenchmarkCharts returns null when it has no panel, so a benchmark with linked results may have no visible explanation of why no comparative plot exists. Evidence: components/catalogue/BenchmarkCharts.tsx:280. Fix: a compact evidence-state block that distinguishes 'no reviewed results', 'individual reported results', 'compatible comparison available', 'conditions incomplete', and 'excluded source evidence'. Show a meaningful diagram or protocol structure where reviewed information exists; never add a decorative rank or pool incompatible results to fill space.

8. **P2 — Historical research gaps compete with current findings.** BenchmarkResearch renders old gaps in full, with a long warning that later extraction may have answered them. Readers must resolve the conflict themselves. Evidence: components/catalogue/BenchmarkResearch.tsx:66–82. Fix: current coverage summary and primary papers first; put the dated search/gap report in 'Literature check history'. Preserve original assertions and review dates; do not silently mark a gap resolved without review.

9. **P2 — Run guidance has inconsistent interaction models and duplicates protocol choices.** RunGuide prints every step, code sample and inline citation at once; RunRecipes hides sequential steps in a select with no Previous/Next or progress cue. Protocols are listed under Evaluation design and then again in Run this benchmark. Evidence: components/catalogue/RunGuide.tsx:96–148; components/catalogue/RunRecipes.tsx:66–83, :119–169; app/database/[kind]/[id]/page.tsx:548–577. Fix: a concise runnable-status summary with scope, data, hardware and execution status; a visible ordered step list/stepper for a chosen protocol. Keep supplied-prediction rescoring and model execution distinct, and do not equate smoke tests with reproduction. Move this flow to a dedicated section reached by a clear action.

10. **P2 — Accessibility foundations are good, but recovery/orientation need work.** Most filters are labelled; disclosures are native; scrollable catalogue tables are focusable; loading notices are live; chart values have text equivalents. However layout has no skip link/main target (app/layout.tsx:22); the mobile menu has aria-expanded but no aria-controls (components/header.tsx:43–55); repeated result-selection checkbox labels omit the record name (Explorer.tsx:317–334); async Results totals are outside the live region, leaving only transient loading text announced (Results.tsx:96–102, :159–172). MFASS v2 horizontal table wrappers lack the focusable named-region pattern already used elsewhere (app/runs/mfass-v2/page.tsx:32, :39). Fix these through focused keyboard and screen-reader testing; do not label the site broadly inaccessible on source inspection alone.

11. **P3 — Type and spacing weaken the reading hierarchy.** Small mono status text (11px), repeated muted 12–13px citations and long 920px paragraphs compete with a large number of identically styled 25px section headings. Evidence: database.module.css:24–27, :104–107, :129–131, :364–369, :401–403. Fix: content measure near 65–75ch for prose; full width for data; fewer top-level headings; 14px secondary text and compact status tokens with plain-language definitions. This is a readability recommendation, not a claimed contrast failure.

12. **P3 — Evidence landing page leads with export mechanics instead of interpretation.** Downloads, field paths, JSON typing and CSV formula escaping appear before 'Read the review scope first'. Evidence: app/evidence/page.tsx:63–105. Fix: 'What does source checked mean?' and the four scope definitions first; offer downloads immediately as a secondary action, but place schema instructions under 'For data users'.

## Proposed hierarchy

- Home: one-line purpose → search → Models / Benchmarks / Datasets / Results with optional advanced kinds → active filters and result count → compact scannable records → short evidence-status explanation → coverage/downloads.
- Model: identity and biological purpose → reviewed input/model/output diagram and three key facts → evaluation coverage → Results by protocol/configuration → How it works → specifications/limitations → Evidence.
- Benchmark: biological question and what is measured → task/protocol/dataset diagram or compact structure → evidence availability → Results within selected protocol → Run selected protocol → limitations → Evidence/history.
- Result/evaluation: value, metric and direction → exact tested entity, protocol, dataset/split, origin, coverage and uncertainty → sibling metrics from that evaluation → source/provenance → reproduction status.
- Evidence: status meaning and scope → claim/source inspection → review history → exports and technical schema.

## Minimum first iteration

Move benchmark overview before results, apply progressive disclosure consistently, replace primary browse cards with compact structured records, add filter reset and truthful empty states, make on-page navigation conditional and persistent, and compress provenance into coherent Evidence sections. Keep source records, version IDs, units, coverage, review scope and comparison restrictions intact. Then validate realistic desktop/mobile tasks with existing good-data, sparse-data, excluded-evidence and superseded records.
