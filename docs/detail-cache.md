# Dependency-keyed detail cache

`npm run build:cached` is an opt-in prototype for issue #89. It prepares the pinned current release, computes explicit input manifests for canonical result/source pages, and skips rendering compatible cache hits. Other entity kinds and aliases render normally. Ordinary builds and PR smoke exports do not use this cache.

The manifests capture record detail, exact result/evidence responses (including totals and cursors), metadata, linked family/identity/reproduction records, and resolved use-case backlinks. The renderer epoch includes application/component/query code, dependency and build configuration, effective public environment, runtime and Footer year. Release provenance is a dependency: a new release deliberately invalidates every cached page. This is not a claim of cross-release reuse.

Entries preserve both HTML and Next's RSC `index.txt`, with checksums. After each build, the orchestrator verifies every shared static asset and every leaf page chunk referenced by the cached HTML/RSC. Unrelated entity page chunks may differ. A missing or incompatible asset forces a complete render before restoring output. One anchor page per cached kind always renders. Unsupported records are never skipped; missing or corrupt cache entries must be misses.

Cache data and reports live under ignored `.detail-cache/`. Use `npx tsx scripts/detail-cache/run.ts --no-cache` after hydration for a clean-render comparison with the same deterministic build ID. A normal full build remains the fallback. Never run a sampled export through this cache.

Dependency lists are intentionally explicit and reviewed alongside the corresponding detail components. A new query/read requires updating its manifest and mutation tests. The cache is not enabled in deployment CI until its measured benefit and storage cost justify that choice.

On the 2026-10-06 BRCA release, local builds measured 253.2 seconds cold, 202.0 seconds unchanged, 206.1 seconds after changing one source title, and 271.6 seconds for a clean build of the same edited data. The unchanged run reused 13,276 of 13,278 eligible canonical pages; the edit reused 12,876. It changed one source and 400 linked results, exactly the 401 dependency keys predicted before the build. Each run rendered two anchors; none needed an asset fallback. The cold and unchanged result/source HTML and RSC payloads matched byte for byte. All 26,556 result/source HTML and RSC payloads in the edited cached export matched the edited clean export after normalizing only Next's different webpack runtime filename. The local cache occupies about 2.1 GB on disk, so production CI does not transfer it. A new release invalidates the entire cache.

To repeat the controlled update, hydrate the reviewed current release, run this cache once cold and once unchanged, then work only on an ignored local copy of `public/omics/catalogue.json`. Save its exact bytes and SHA-256, change the `name` of `acquired-source-a1e1af10cf13322916ca` in a copy, and atomically replace the local catalogue file (do not write through a possible hard link). Run the cached build, then `npx tsx scripts/detail-cache/run.ts --no-cache` with the same temporary bytes. Compare every result/source `index.html` and `index.txt`; webpack runtime filenames can differ between builds. Restore the original bytes in a `finally` block, verify their SHA-256 and the pinned release copy, and rerun `npm run data:prepare -- --current-only`. Never publish the temporary fixture output.

Cache keys preserve JSON object insertion order because technical metadata is displayed in that order. The runner snapshots the catalogue and enabled use-case manifest/artifact bytes before constructing its queries, and rejects any changed inputs or renderer epoch after either the initial or fallback build. A concurrent edit therefore fails the build rather than saving output under an obsolete key.
